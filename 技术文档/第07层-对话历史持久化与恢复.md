# Aix-DB 功能复刻：第 07 层——对话历史持久化与恢复

## 1. 本层目标

完成普通问答从生成、保存到恢复的真实闭环：

```text
用户发送问题
  → Sanic 流式调用 LLM
  → 前端实时渲染回答
  → 后端收集回答分片
  → 写入 t_user_qa_record
  → 历史侧栏按 chat_id 展示会话
  → 点击会话查询全部问答记录
  → 将数据库答案重新转换为可读流
  → MarkdownPreview 恢复完整对话
  → 支持搜索、分页和整组删除
```

本层只完成 `COMMON_QA` 普通问答的历史闭环。数据问答、文件问答以及其业务数据将在后续功能层继续覆盖。

## 3. 数据库记录结构

历史记录保存在 PostgreSQL 表：

```text
t_user_qa_record
```

本层重点字段：

```text
id              数据库记录 ID
user_id         当前登录用户 ID
uuid            单条消息唯一 ID
chat_id         一组会话的唯一 ID
question        用户问题
to2_answer      LLM 文本答案 JSON
to4_answer      后续业务数据 JSON
qa_type         问答类型
datasource_id   数据源 ID
file_key        文件信息
sql_statement   数据问答 SQL
create_time     创建时间
```

同一个 `chat_id` 可以包含多条问答记录。历史侧栏按 `chat_id` 去重，只显示每组会话的第一条问题；打开会话时再查询该 `chat_id` 下的全部记录。

`to2_answer` 不是直接保存纯文本，而是保存与流式协议兼容的 JSON：

```json
{
  "data": {
    "messageType": "continue",
    "content": "模型完整回答"
  },
  "dataType": "t02"
}
```

## 4. 后端执行顺序

1. 确认 `TUserQaRecord` 模型和数据库表存在。
2. 确认历史请求 Schema 已存在。
3. 验证 `add_user_record()` 可以写入当前用户记录。
4. 验证历史列表、会话详情和删除服务。
5. 在 `LLMRequest.exec_query()` 中收集流式回答分片。
6. 正常完成后调用 `add_user_record()`。
7. 取消生成时跳过保存。
8. 保存异常时记录日志，但仍正常结束回答流。
9. 启动 Sanic 并执行历史 API 联调。

启动后端：

```powershell
uv run python serv.py --env=dev
```

## 5. LLM 回答保存逻辑

`services/llm_service.py` 在开始生成前读取本次会话信息：

```python
query = req_obj["query"]
uuid_str = req_obj.get("uuid")
chat_id = req_obj.get("chat_id")
qa_type = req_obj.get("qa_type", "COMMON_QA")
file_list = req_obj.get("file_list") or []
datasource_id = req_obj.get("datasource_id")
answer_chunks = []
```

每次收到 LLM 文本分片时同时执行两件事：

```python
answer_chunks.append(text)
await self._send_text(response, text)
```

流式回答正常结束后保存记录：

```python
if not task_context["cancelled"] and uuid_str and chat_id:
    await add_user_record(
        uuid_str=uuid_str,
        chat_id=chat_id,
        question=query,
        to2_answer=answer_chunks,
        to4_answer={},
        qa_type=qa_type,
        user_token=token,
        file_list=file_list,
        datasource_id=datasource_id,
    )
```

必须遵守以下顺序：

```text
发送 continue 分片
  → 正常完成后保存数据库
  → 发送 messageType=end
  → finally 发送 dataType=t99
  → 清理 running_tasks
```

数据库保存需要独立的 `try/except`。即使数据库临时不可用，也不能破坏用户已经收到的回答，更不能丢失 `end` 和 `t99` 结束事件。

## 6. 用户记录服务

`add_user_record()` 首先从 JWT 解出用户 ID：

```python
user_info = await decode_jwt_token(user_token)
user_id = user_info.get("id")
```

然后把回答分片拼成完整内容：

```python
t02_content = "".join(
    str(item) for item in (to2_answer or [])
)
```

最后插入 `t_user_qa_record` 并通过 `RETURNING id` 返回新记录 ID。

历史服务职责：

```text
query_user_record_list()
  按 user_id 查询
  按 chat_id 去重
  返回侧栏必要字段
  支持 question 关键词搜索和分页

query_user_record()
  指定 chat_id 时返回该会话的所有记录
  按 id ASC 保证问答恢复顺序
  返回答案、业务数据和数据源名称

delete_user_record()
  同时使用 user_id 和 chat_id 删除
  一次删除整组会话记录

get_record_sql()
  使用 record_id 和 user_id 查询
  为历史数据问答图表恢复 SQL
```

所有详情查询必须同时限制当前 `user_id` 和目标 `chat_id`，搜索条件必须参数化，不能让其他用户通过猜测 `chat_id` 读取会话。本层联调时应把用户隔离作为必要检查项。

## 7. 历史 REST API

本层使用四个 JWT 保护接口：

```text
POST /user/query_user_record_list
POST /user/query_user_record
POST /user/delete_user_record
POST /user/get_record_sql
```

前端统一通过 `authenticatedPost()` 添加请求头：

```ts
headers: {
  'Content-Type': 'application/json',
  Authorization: `Bearer ${token}`,
}
```

历史列表请求：

```json
{
  "page": 1,
  "size": 20,
  "search_text": "PostgreSQL"
}
```

会话详情请求：

```json
{
  "page": 1,
  "size": 100,
  "search_text": "",
  "chat_id": "目标会话ID"
}
```

删除会话请求中的 `record_ids` 实际承载 `chat_id` 列表：

```json
{
  "record_ids": [
    "目标会话ID"
  ]
}
```

这个命名沿用源码 Schema。复刻时不要误传数据库记录 `id`，否则无法删除整组会话。

## 9. 前端历史 API 封装

`web/src/api/index.ts` 提供：

```ts
queryUserRecordList(page, size, searchText)
queryUserRecords(chatId, page, size)
deleteUserRecords(chatIds)
get_record_sql(recordId)
```

接口函数保持职责单一：只负责 Token、URL、请求方法和请求体。分页拼接、会话恢复以及错误提示由聊天页面处理。

接口返回 `401` 时，聊天页面必须跳转 `/login`；其他非成功状态进入历史错误提示。

## 10. 历史答案流适配

`MarkdownPreview` 原本消费实时回答的 `ReadableStream`，数据库返回的却是已经完成的字符串。为了复用同一套 Markdown 渲染链路，本层新增：

```text
web/src/store/business/initChatHistory.ts
```

第一步，解析数据库中的 `to2_answer`：

```ts
parseStoredAnswer(record.to2_answer)
```

第二步，把完整答案包装成单次输出的字节流：

```ts
createHistoryReader(answer)
```

适配器输出的数据结构：

```json
{
  "messageType": "continue",
  "content": "历史回答"
}
```

注意这里传给前端 Transformer 的是顶层 `messageType` 和 `content`，不能再次包成 `{ data: {...} }`，否则标准 Markdown Transformer 无法提取内容。

因此 `MarkdownPreview` 的 `reader` 类型需要同时接受：

```ts
ReadableStreamDefaultReader<string>
ReadableStreamDefaultReader<Uint8Array>
```

实时回答使用字符串 Reader，历史适配器使用字节 Reader。

## 11. 聊天页历史状态

`web/src/views/chat/index.vue` 增加以下状态：

```text
historyItems           当前页会话列表
historyLoading         侧栏加载状态
historyDetailLoading   会话详情加载状态
historyError           历史错误提示
historySearchText      搜索关键词
historyPage            当前页
historyTotalCount      会话总数
historyTotalPages      总页数
```

页面挂载时加载第一页：

```ts
onMounted(() => {
  loadHistory()
})
```

实时回答完成后刷新第一页，使刚完成的会话立即出现在侧栏：

```ts
if (!conversationItems.value[index]?.isHistory) {
  loadHistory(1)
}
```

历史消息不能触发这个刷新，否则恢复一组历史记录时，每个 Markdown 组件完成渲染都会重复请求列表。

## 12. openHistory 的来源和职责

`openHistory` 不是 Vue、Pinia 或 API 模块提供的方法，也不是从 Aix-DB 的其他文件自动导入的方法。它直接定义在：

```text
web/src/views/chat/index.vue
```

点击历史项时通过模板调用：

```vue
@click="openHistory(item)"
```

执行顺序：

```text
读取 item.chat_id
  → 每页查询 100 条详情
  → 根据 total_pages 循环加载全部页面
  → 每条数据库记录拆成 user 和 assistant 两项
  → assistant 答案创建历史 Reader
  → 更新当前 chatId
  → 替换 conversationItems
  → 清理旧 Writer
  → 滚动到底部
```

必须循环读取全部详情页，不能只请求前 100 条，否则超长会话会被静默截断。

恢复后的消息标记：

```ts
isHistory: true
```

并传给 Markdown 组件：

```vue
:is-init="item.isHistory ?? false"
```

这样历史内容会按初始化模式快速渲染，而不是重新播放实时打字效果。

## 13. 搜索、分页和删除

搜索规则：

```text
输入 question 关键词
  → loadHistory(1)
  → 后端按当前 user_id 过滤
  → 按 chat_id 去重
  → 返回匹配会话
```

清空搜索后重新加载第一页。

分页规则：

```text
每页 20 个会话
上一页在 page <= 1 时禁用
下一页在 page >= total_pages 时禁用
```

删除前使用确认框。删除当前打开的会话后调用 `newChat()`；如果删除的是某页最后一项并且当前页大于 1，则回退到上一页。
